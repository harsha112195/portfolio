Work

Public-sector reporting form

A public-sector team takes reports of suspected abuse and neglect of vulnerable adults through a legacy vanilla JavaScript form. I'm one of the frontend developers rebuilding it as a React single-page app: eight steps, eleven pages, no login, used by members of the public.

RoleFrontend developer
StackReact 19, TypeScript, Vite, TanStack Router, React Hook Form, Zod, Zustand, Tailwind v4, shadcn/ui
Shapepnpm monorepo with shared UI, validation, types and API-client packages
DeliveryAzure DevOps, deployed to Azure Red Hat OpenShift through DEV, QA and PROD

  • The old form is the spec

    Behavior has to match the system people already rely on, so I inventory every field against the acceptance criteria and the legacy source before writing a component. Every error string lives in one error-messages.ts file, so inline messages and the summary banner can't drift apart.

  • Form state that survives real use

    React Hook Form handles fields, Zod handles rules, and a Zustand store holds the wizard, persisted to session storage so a refresh doesn't lose a half-finished report. Each submission carries a generated idempotency key, so a double click or a retry can't file the same report twice.

  • Bugs that only show up in production builds

    Pill-style radio groups registered inside useEffect had a timing race that React StrictMode hid in development. Moving them to useController fixed it, and I now verify with pnpm build && pnpm preview instead of trusting the dev server. Another one: React Hook Form treats defaultValues as a one-time snapshot, so values leaked through navigate-away-and-back until I reset the form with methods.reset().

  • A shared component layer

    FormField, PillRadio, AddressBlock, DobAgeRow, collapsible card sections and a page-level error summary are built once and reused across steps. Clearing inline errors on change lives in a single wrapper, so every step behaves the same way.

  • End-to-end coverage with Playwright

    I'm writing Playwright end-to-end tests that exercise complete user workflows through the form, so each release is checked against existing behavior before it ships.

The source belongs to the client, so there's no repository link. The demo below is original code that shows the same patterns.

Marketing site

A staffing firm's public site

I built a marketing site for a small staffing firm in Next.js (App Router), TypeScript and Tailwind, with a Sanity studio so non-developers can edit copy. This is a lightweight preview of its design and behavior, running as plain JavaScript on this page. It is not the Next.js app itself.   • Content lives in a CMS, with a safety net

    Pages read from Sanity with GROQ and revalidate on a timer. If the CMS is unreachable or empty, the site falls back to typed local content, so a bad deploy or a missing token never produces a blank page.

  • One typed content contract

    The content shapes live in a shared package that both the site and the fallback use, so a schema change shows up as a compile error instead of a runtime surprise.

  • The contact form fails loudly and safely

    Server-side validation, a honeypot field, an optional webhook, and an error summary that moves focus to the first problem. Playwright tests cover it on desktop and phone viewports.

  • Static where it can be

    Industry pages are generated from the CMS slugs, with per-page metadata, a sitemap and a robots file. Only the form is client code.

Status: the Next.js app is written and tested in pieces; the preview above is the fastest way to see it without a deploy.

Digital client-experience platform

An example of the frontend work this portfolio covers: campaign pages and internal portals in React and TypeScript, built with marketing, UX and product. It shows the scope and working style, and is not a record of one specific engagement.

StackReact, TypeScript, REST services, analytics tags
PartnersMarketing, UX, product and API teams
FocusLaunch speed, conversion, performance, maintainability

  • A landing-page system, not one-off pages

    Reusable, responsive templates and modular sections (hero banners, product feature panels, FAQs, lead-generation forms and calls to action) so a new campaign launches by assembling pieces instead of starting a page from scratch.

  • From brief and Figma to a finished page

    Campaign briefs and Figma designs become polished pages through repeated rounds with marketing, UX and product, tuning the message hierarchy, the layout and the path to conversion.

  • Content and data from REST services

    Content and product information flow from REST services into reusable components, with dynamic rendering, form validation, and consistent loading and error states.

  • Discoverable and accessible

    Semantic HTML, page metadata, canonical URLs, structured content and accessible navigation, so pages are easy to find and easy to use.

  • Measured, then refined

    Page views, CTA clicks and form conversions are tracked through analytics tags. A/B experiments on page content and calls to action feed the next round of UI changes.

  • Performance work

    Responsive image handling, lazy loading, code splitting and fewer unnecessary React renders, plus smaller bundles, better asset delivery and fixes for browser-specific issues.

  • Internal enterprise portals

    React and TypeScript features with a clear information hierarchy and consistent interaction patterns: data-rich dashboards and workflow screens with client-side state, validation and error handling, built on a maintainable UI architecture.

  • Delivery inside a larger team

    Frontend changes are coordinated with Java, Spring Boot and Python service teams during the modernization of legacy workflows, with automated testing, peer reviews, release validation and production defect triage in an Agile team.
